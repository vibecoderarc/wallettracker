# Deploying to Render

`render.yaml` at the repo root is a Blueprint: Render reads it and creates
everything in one go. You should not need to click through service creation by hand.

## What gets created

| Service | What it is | Notes |
| --- | --- | --- |
| `alphagraph-api` | FastAPI | The only service that touches the database |
| `alphagraph-web` | Next.js dashboard | Server-rendered; calls the API over HTTP |
| `alphagraph-nightly` | Cron job, 07:00 UTC | Grading, discovery sweep, digest |
| `alphagraph-db` | Postgres 16 | |

## Steps

1. **Render → New → Blueprint**, pick this repo, let it read `render.yaml`.
2. Render prompts for the `sync: false` variables. On the first deploy you can
   leave the provider credentials blank — the system runs on fixtures and says so
   on the System screen rather than pretending to have data.
3. Deploy. The API comes up first; the web service waits on it for its URL.
4. Seed some data so the dashboard is not empty — see below.

You do **not** need to configure CORS. Every dashboard page is a server
component, so its calls to the API happen server-to-server inside Render and
never involve a browser origin. `ALPHAGRAPH_CORS_ORIGINS` matters only if you
later add something that calls the API directly from the browser.

## The API token

`ALPHAGRAPH_API_TOKEN` is generated by Render and injected into all three
services, so they always agree and you never handle it.

Every endpoint except `/v1/health` requires `Authorization: Bearer <token>`.
Health is deliberately open so Render's health check works without a secret, and
it returns nothing beyond a status and the run mode.

**The API will refuse to start** if `ALPHAGRAPH_ENVIRONMENT` is anything other
than local/dev/test and no token is set. This is intentional: an unauthenticated
public hostname would hand your tracked wallets, dossier notes, and hypotheses to
anyone who found the URL — which is the whole product.

To call it yourself, copy the value from the API service's Environment tab:

```bash
curl -H "Authorization: Bearer $TOKEN" https://alphagraph-api.onrender.com/v1/candidates
```

## Seeding data

The database starts empty, so the dashboard comes up with empty states — "No
signals yet", "No candidates pending" — rather than errors. That is working
correctly; it just has nothing to show.

To populate it from the fixture world, open a **Render Shell** on
`alphagraph-api` and run:

```bash
alphagraph demo
```

This writes ~11.5k events, 429 assets, five discovered candidates and ~2.2k
replayed signals. It takes a couple of minutes on a laptop and noticeably longer
on a Starter instance's shared CPU — expect five to fifteen minutes, and do not
close the shell while it runs.

Afterwards the dashboard has data on every screen and the nightly cron keeps it
moving.

## Postgres compatibility

The full suite and the end-to-end demo have both been run against PostgreSQL 16,
not only the SQLite used in development. That flushed out one real defect — a
primary-key lookup that SQLite tolerated and Postgres rejected — which is fixed.

If you change persistence code, run the suite against Postgres before deploying:

```bash
createdb alphagraph_pytest
ALPHAGRAPH_TEST_DATABASE_URL=postgresql+psycopg://user:pass@localhost/alphagraph_pytest \
  pytest -q
```

## Schema management

Tables are created with SQLAlchemy's `create_all()` at startup. That is adequate
while the schema only ever grows, and it is what the deploy currently relies on.

It does **not** handle column changes or drops. Alembic is already a dependency
but no migrations have been written. Before the first schema change that alters
or removes a column, generate an initial migration and switch the start command
to run `alembic upgrade head` — otherwise that deploy will fail confusingly, or
worse, appear to succeed against a stale schema.

## Costs

Roughly $7/service/month on Starter plus the Postgres plan. Three services and a
database, so budget around $25–30/month before any data provider.

The Free tier will not work well here: free web services sleep after inactivity,
and a sleeping API means the dashboard shows connection errors until it wakes.

## Going live with real data

1. Implement the interfaces in `packages/alphagraph/providers/base.py` against a
   real vendor.
2. Set `ALPHAGRAPH_SOLANA_RPC_URL` and friends.
3. Set `ALPHAGRAPH_PROVIDER_MODE=live`. The service refuses to boot in live mode
   without a chain provider configured, rather than reporting empty coverage.
4. Leave `ALPHAGRAPH_RUN_MODE=shadow` until you have reviewed a few weeks of
   shadow output. Notifications need *both* `live_alerts` and a destination.

## Things that will bite you

- **Cron timing is UTC.** `0 7 * * *` is 07:00 UTC, not your local morning.
- **The nightly job needs the same database.** It is wired via `fromDatabase` in
  the blueprint; do not point it elsewhere.
- **Region matters.** All services are pinned to `oregon` so the API and database
  are not talking across regions. Change all of them together or none.
- **`hostport` gives host:port, not a URL.** If you rewire the web service's
  `ALPHAGRAPH_API_URL` by hand, include the scheme.
